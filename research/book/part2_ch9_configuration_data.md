## 9.0 Chapter purpose and problem map

Configuration and engineering data management in automotive is dominated by ARXML, the AUTOSAR XML schema. ARXML is the lingua franca of the engineering toolchain: it carries system descriptions, ECU extracts, software component descriptions, interface definitions, and configuration parameters. The research record shows that ARXML is massive, version-fragile, non-canonical, and poorly diffable; that variant management is complex and error-prone; that PLM and engineering data are poorly integrated; and that manual "glue work" fills the gaps between tools.

## 9.1 ARXML as the lingua franca

ARXML is text-based and VCS-manageable, but different tools generate XML tags in different orders, producing massive, meaningless diffs. Semantic merge conflicts are common. Schema version mismatch breaks import. No canonical serialisation is mandated strongly enough to prevent this (W2-015, W4-002, W1-013). Large projects (Audi BUSNET) face data volume and performance bottlenecks (W2-015).

Key friction points:

- **Tag reordering** makes code review of ARXML nearly impossible (autosar.io guide, cited in W1-013, W2-015).
- **Interface definitions in ARXML drift from Simulink models**, causing integration failures when interface definitions mismatch (W1-013).
- **Schema differs across releases** (CP R4.4.0 vs R4.3.1), so a file generated by one tool may not import into another (W4-002, W2-001).
- **Hand-editing is impractical**: a single typo in a reference path breaks the whole configuration (W2-001, W4-003).
- **No abstraction layer between engineer intent and serialized XML**: all variability is pushed into data (W2-001).

**Automation feasibility:** High for canonicalisation, diff normalisation, consistency checks, and config generation from higher-level models. AI applicability is Medium–High for schema-aware assistants and ARXML intelligence.

## 9.2 Variant management (W1-011, W2-011, W3-011, W4-005)

Vehicle variants (hardware, software, region, regulation) explode combinatorially. AUTOSAR supports variants at multiple binding times (SystemDesign, CodeGen, PreCompile, Link, PostBuild) with complex condition logic; variant explosion across vehicle lines; consistency of variant conditions across tools; postbuild variants require runtime handling (W2-011). MathWorks documents many variant configuration paths; errors surface late. No single source of truth for variant conditions exists (W2-011, W4-005).

Variant explosion propagates into test environments: HIL setup latency and reconfiguration takes weeks per variant (W3-011), and combinatorial testing multiplies (CQ-015, CQ-030). The question of whether variant management can be unified across system (W1-011), AUTOSAR binding-time (W2-011), and test (W3-011) dimensions, or whether these are fundamentally different variability models, remains open (CQ-015).

## 9.3 RTE contract and generation (W2-012)

RTE generation has a contract phase (RTE contract, BSW scheduler contract, PreBuild data set) that must align across tools. Inconsistent component implementations are rejected at compile time, but semantic errors (mapping, timing) surface later. RTE generation is ECU-specific and must be regenerated per mapping; multi-ECU composition consistency is manual (W2-012). Contract phase must be repeated for each change; no incremental regeneration standard exists.

---

## 9.4 PLM/PDM integration (W4-024)

PLM/PDM systems and engineering data (ARXML) are poorly integrated. Parallel versioning creates synchronization risk: a change in PLM may not propagate to ARXML, and vice versa. Manual sync is required, and data exchange failures between OEM and suppliers are common (W4-024, W4-023). The interaction between PLM↔ARXML integration failure and configuration drift (W1-013, W2-001) and safety-case maintenance (W4-012) is a documented cross-domain dependency (CQ-016).

---

## 9.5 Glue work (W4-028)

Manual data transformation via spreadsheets and scripts fills gaps between tools. This "glue work" is estimated at 10–30% of engineering effort (hypothesis, not measured) and is a symptom of tool fragmentation and lack of canonical data flow (W4-028, W4-001). It is invisible in project plans and accumulates as technical debt.

---

## 9.6 Test data management (W3-030)

Test data management and artifact versioning across XiL (MIL/SIL/PIL/HIL) is not standardised. Test artifacts (stimuli, expected results, environment configurations) must be versioned alongside software and configuration, but tooling does not support this consistently (W3-030). This contributes to non-reproducible test failures and horizontal traceability gaps (W3-023).

---

## 9.7 Traceability (W4-007, W1-003, W3-023)

End-to-end traceability (requirements → design → code → tests → safety evidence) is mandated but manual and brittle (W4-007, W1-003). Links go stale after changes; engineers fear creating wrong links; cross-domain traceability (ML models, datasets, ODDs, scenarios) is harder (W3-023, W1-004). Horizontal traceability across MIL–SIL–HIL is particularly weak (W3-023). Tooling stores links but does not validate semantic correctness (W1-002).

---

## 9.8 Supplier/OEM data exchange (W4-023)

Supplier/OEM toolchain mismatch and data exchange friction arise from format incompatibilities, version drift, and differing tool profiles (W4-023, W2-005). OEMs and suppliers use different tools, versions, and extensions; ARXML import/export is lossy; MCAL must be configured in the vendor's tool and only referenced by others. The cost and frequency of these failures are unquantified (CQ-047).

---

## 9.9 Cross-cutting root causes

1. **ARXML is the bottleneck**: massive, version-fragile, non-canonical, poorly diffable (W2-001, W2-015, W4-002, W4-003).
2. **No canonical serialisation** is enforced across tools (W2-015, W4-002, W1-013).
3. **Variant management is immature** and multiplies combinatorially across system, AUTOSAR, and test dimensions (W1-011, W2-011, W3-011, W4-005).
4. **PLM and engineering data are poorly integrated**, creating parallel versioning risk (W4-024).
5. **Glue work** fills tool gaps and is invisible and unmeasured (W4-028).
6. **Traceability is manual and brittle**, with no semantic validation of links (W4-007, W1-003, W3-023).
7. **Supplier/OEM data exchange is friction-heavy** and version-sensitive (W4-023, W2-005).

---

## 9.10 Evidence limitations

- The 10–30% glue-work figure is a hypothesis, not a measurement (W4-028).
- ARXML-related rework cost is unquantified; "hours–days per incident" is anecdotal (CQ-013).
- Variant explosion cost is cited everywhere but never quantified (CQ-030).
- Tool-specific claims (autosar.io, Vector, MathWorks) reflect vendor positioning and should be treated as indicative.
- PLM integration findings rely on vendor and practitioner sources; no independent study is cited.
